## 1. 先看已有的轮子（调研结论）

商业归因在广告和联盟营销两侧都有十年以上的成熟结构。**两周里最不该做的事就是自己发明一套。** 三个先例：

| 先例 | 它解决什么 | 我们借什么 | 我们偏离什么 |
|---|---|---|---|
| **IAB SupplyChain（schain）**<br>OpenRTB `source.schain` | 一次竞价请求从发布方到买方，途经哪些拿钱的中间方，按跳有序记录 | **整个链结构**：有序 `nodes` 数组、`complete` 完整性标志、`hp` 是否参与资金流、节点标识经发现文档（`sellers.json`）解析 | **schain 不签名**——每一跳的声明都是自述，篡改与伪造无法检测。这是它公开的已知弱点，也正是我们要做签名的全部理由 |
| **联盟营销 click_id + S2S postback** | 点击时发 ID，转化时由商户服务端回报，凭 ID 匹配记账 | **核销机制**：凭证在「意图发生时」签发而非转化时推断；`txn_id`（我们叫 `order_id`）做转化去重；last-click 作为默认裁决规则 | 联盟的 click_id 是**不透明串**，语义全在网络方数据库里。我们的凭证**自带可验证语义**，第三方离线即可判定归谁 |
| **AP2 mandate / Visa TAP** | 代理身份背书与用户授权的不可抵赖 | **签名即事实**的思路：AP2 的 mandate 是绑定用户密钥对的防篡改产物；TAP 让代理用私钥签 HTTP 请求、商户对注册表验证 | 它们锚在**支付**环节。OCP Catalog 在**发现**环节，上游得多，所以我们的凭证签发点是 resolve，不是 checkout |

**一句话定位**：ACP 明确不做代理身份背书，schain 有链但不签名，联盟有核销但凭证不透明。**OCP 要做的是「签名的 schain + 透明的 click_id」**，落在发现层。这个位置目前没有既有标准占据。

> 结构上大量对齐 schain 是刻意的：将来要和广告 / 联盟侧的结算系统对账时，同构的数据模型比自创字段便宜得多。

## 2. 数据模型骨架

三个对象，职责不重叠：

| 对象 | 谁产生 | 作用 |
|---|---|---|
| `AttributionToken` | 目录节点，在 `resolve` 时 | 「**是我把这个对象送到这个代理面前的**」——带签名的事实声明 |
| `AttributionChainNode` | 每一跳目录节点 | 多跳转发时，每跳追加一个节点并对**截至本跳的链前缀**签名 |
| `ConversionReport` | 商户，在成交时 | 「**这笔订单成交了，金额 X，凭证是 Y**」——闭环的另一半 |

**锚点选在 resolve**，两条理由（沿用 7 周计划的实测结论）：

- `resolveRequestSchema` / `actionBindingSchema` 均**非** `.strict()`，加可选字段零破坏；`catalogQueryRequestSchema` 是 `.strict()`，本期不碰
- `purpose: "checkout"` 本就标识转化意图，是天然的签发触发点

**金额一律用最小单位整数**（`amount_minor: 12900` + `currency: "CNY"`），不用浮点。这不是洁癖：canonical 规范 §7 的 Level 1 只接受安全整数，浮点数在三语言间的字节表示无法统一，**用浮点承载金额会让凭证在跨语言验签时直接失败**。W1 的约束在这里变成了设计收益。

**逐跳签名，不是终端单签。** 只让最后一跳签名的话，上游节点的声明仍然不可验证——那就退回成了 schain 的原问题。分账要用的东西，每一跳都得自己背书。

**裁决规则默认 last-touch**（最后一跳目录节点得全额），写进规范并标注可配置。规则必须写下来：多个凭证争同一订单时若无成文规则，结算方会各自解释，对账必然出分歧。

## 3. 逐任务计划

### 第 1 周（09-14 ~ 09-18）· 可验证的归因事实

| 小任务 | 天 | 内容 | 完成判据 |
|---|---|---|---|
| **T1** | 周一二 | ① `docs/specs/attribution/v1.md`：claims 定稿、链结构、裁决规则、失败语义<br>② `ocp.catalog.attribution.v1/` JSON Schema<br>③ Zod 零破坏挂载：`actionBindingSchema.attribution`、`resolveRequestSchema.attribution_context`（均可选） | claims **逐条写明存在理由**，无「以防万一」字段；**不含 attribution 的旧 payload 必须仍然通过校验** |
| **T2** | 周三四 | ① `packages/ocp-crypto` 包骨架 + TS `canonicalize()`（W1-T3 顺延进来）<br>② Ed25519 keygen / sign / verify<br>③ **补 `wellKnownCatalogDiscoverySchema` 进 `ocp-schema` + `jwks_url`**（历史欠账：该响应体目前无任何 schema）<br>④ JWKS 加载、`kid` 解析、TTL 缓存 | 75 条向量全绿；**三条错误路径有测试**：`kid` 未命中 / JWKS 过期 / 算法不支持 |
| **T3** | 周五 | 目录节点在 `purpose: "checkout"` 的 resolve 上签发 token，嵌入 `action_binding.attribution` | resolve 响应含 attribution 且 schema 校验通过；`curl` 取到公钥后**离线**验通 |

**周五演示**：起节点 → resolve 一个对象 → 拿到带签名的归因凭证 → 断网状态下用公钥验通。

### 第 2 周（09-21 ~ 09-25）· 链路闭环与核销

| 小任务 | 天 | 内容 | 完成判据 |
|---|---|---|---|
| **T4** | 周一二 | ① 多跳：每跳追加 `AttributionChainNode` 并对链前缀签名<br>② 验证器：逐节点验签 + `complete` 判定<br>③ `jti` 防重放（内存 TTL 缓存，**明确标注生产需持久化**） | 三跳链逐跳验通；篡改中间节点 → 错误**精确定位到第几跳**；同一 `jti` 重放 → 拒绝 |
| **T5** | 周三四 | ① Provider 侧验证参考实现（独立小脚本，模拟商户收单）<br>② `ConversionReport` 回报：`{attribution_token, order_id, amount_minor, currency}`<br>③ `order_id` 去重（联盟 `txn_id` 同构）<br>④ last-touch 裁决实现 | 同一 `order_id` 回报两次**只记一次**；两个凭证争同一订单 → 按规则裁出**唯一**赢家 |
| **T6** | 周五 | ① CLI `ocp attribution verify` + `ocp catalog resolve --verify-attribution`<br>② 端到端演示脚本<br>③ 零破坏回归 | 六条断言逐条打印通过；`bun run typecheck && bun test` 绿 |

**周五演示——六条断言**：

| | 断言 |
|---|---|
| ✅ | 完整链路 query → resolve → 签发 → 商户验签 → 回报 → 裁决，归到正确的目录节点 |
| ✅ | 三跳链逐跳验签通过，`complete = true` |
| ❌ | 篡改 `agent_id` → 验签失败 |
| ❌ | 超过 `expires_at` → 拒绝 |
| ❌ | 重放同一 `jti` → 拒绝 |
| ❌ | 同一 `order_id` 重复回报 → 只计一次 |

> 前两条证明它**能用**，后四条证明它**骗不了**。分账场景里后四条才是价值所在。

## 附录 · 一个需要主管拍板、但不阻塞开工的问题

**代理身份用谁的？** 归因凭证里要有「这笔是哪个代理带来的」。目前有两条路：

| 选项 | 含义 | 代价 |
|---|---|---|
| OCP 自有 `agent_id` | 自己定义标识空间 | 快，但与支付侧对不上账 |
| 对齐 Visa TAP / AP2 的代理身份 | 复用支付侧已在做身份背书的注册表 | 需调研与合作窗口 |

**不阻塞**：两条路下这个字段都存在，差别只在取值来源，先按自有 `agent_id` 做，加一个可选的 `agent_identity_source` 留口子即可。但如果公司已经在和 Visa / Google 谈接入，**越早知道越省事**——这个信息我们拿不到，需要主管一句话。
