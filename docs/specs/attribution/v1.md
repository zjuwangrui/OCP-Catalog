# OCP Commercial Attribution v1.0

## 1. 文档定位

本文档定义 OCP Catalog 的**商业归因**协议：一笔成交是谁带来的，如何被第三方**独立验证**。

它回答三个问题：

1. 目录节点把一个商业对象送到代理面前时，留下什么可验证的凭证
2. 凭证经过多跳转发后，每一跳如何各自背书，验证方如何定位篡改点
3. 商户成交后如何回报，多个凭证争同一笔订单时按什么规则裁决

本文档**不定义**签名算法的字节格式细节与密钥发现流程——那些属于 `docs/specs/crypto/`。本文档只在需要处引用。
序列化一律遵循 [OCP Canonical JSON v1.0](../crypto/canonicalization.md)（下称 **OCP-JCS v1**）。

本文档中「必须」「禁止」「应当」按 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 理解。

### 1.1 明确的非目标

| 非目标 | 理由 |
|---|---|
| 资金流转、费率、分账对账 | 本协议只产出**可信的归因事实**，钱怎么分是结算系统的事 |
| 阻止商户**漏报**成交 | 签名能证明「这条回报没被篡改」，不能证明「商户报全了」。这是商业信任问题，密码学解决不了，不要假装能 |
| 中心化的归因仲裁机构 | 裁决规则成文公开（§7），各方独立算得出同一结果 |
| 用户身份、隐私画像 | 凭证里不含任何终端用户标识，见 §9 |

## 2. 设计取舍：借了什么，偏离了什么

商业归因在广告与联盟营销两侧有十年以上的成熟结构。本协议**刻意同构**于既有模型，以便将来与广告/联盟侧结算系统对账。

| 先例 | 借用 | 偏离 |
|---|---|---|
| **IAB SupplyChain（`schain`）** | 有序 `chain` 数组、`complete` 完整性标志、`settles`（对应 `hp`）、节点标识经发现文档解析 | schain **不签名**，每跳声明都是自述。本协议**逐跳签名**——这是本协议存在的全部理由 |
| **联盟营销 click_id + S2S postback** | 凭证在**意图发生时**签发而非转化时推断；`order_id`（对应 `txn_id`）做转化去重；last-touch 默认裁决 | 联盟的 click_id 是**不透明串**，语义全在网络方数据库里。本协议的凭证**自带可验证语义**，第三方离线即可判定归谁 |
| **AP2 mandate / Visa TAP** | 「签名即事实」：绑定密钥对的防篡改产物，商户对注册表验证 | 它们锚在**支付**环节。OCP Catalog 在**发现**环节，上游得多，所以签发点是 `resolve` 而非 checkout |

### 2.1 为什么锚在 resolve

| 理由 | 说明 |
|---|---|
| 语义正确 | `resolveRequestSchema.purpose` 已有 `"checkout"` 取值，它本就标识转化意图，是天然的签发触发点 |
| 零破坏 | `resolveRequestSchema` / `actionBindingSchema` 均**非** `.strict()`，加可选字段不影响既有 payload；`catalogQueryRequestSchema` 是 `.strict()`，本协议**不碰** |
| 粒度合适 | query 返回 N 条结果，为每条签发凭证是浪费；resolve 是「代理决定用这一个」的时刻 |

### 2.2 为什么逐跳签名而不是终端单签

只让最后一跳签名的话，上游节点的声明仍是自述，验证方无法判定链前缀是否被伪造——那就退回成了 schain 的原问题。**分账要用的东西，每一跳都得自己背书。**

代价是签名数量随跳数线性增长。链长有上限（§4.4），实测成本可接受。

### 2.3 为什么金额用最小单位整数

OCP-JCS v1 §7 的 Level 1 只接受安全整数，**浮点数的字节表示在三语言间无法统一**。用浮点承载金额会让凭证在跨语言验签时直接失败。

因此 `amount_minor` 必须是整数（`12900` + `"CNY"` = ￥129.00），禁止 `129.00`。

## 3. 三个对象

| 对象 | 谁产生 | 何时 | 作用 |
|---|---|---|---|
| `AttributionToken` | 目录节点 | `resolve` 响应 | 「是我把这个对象送到这个代理面前的」 |
| `AttributionChainNode` | 每一跳目录节点 | 转发时追加 | 本跳的署名与对**链前缀**的签名 |
| `ConversionReport` | 商户 | 成交时 | 「这笔订单成交了，金额 X，凭证是 Y」 |

外加一个请求侧输入对象：

| 对象 | 谁产生 | 何时 | 作用 |
|---|---|---|---|
| `AttributionContext` | 代理 / 中继节点 | `resolve` 请求 | 告知节点「该归给谁」与「上游凭证是什么」 |

机读 schema 见 [`ocp.catalog.attribution.v1/`](../../../ocp.catalog.attribution.v1/README.md)。

## 4. AttributionToken

### 4.1 claims 定稿（逐条理由）

**本表的验收标准是：每个字段都能回答「删掉它，哪条检查做不成」。回答不上来的字段不进 v1。**

| claim | 类型 | 必填 | 存在理由（删掉它会怎样） |
|---|---|---|---|
| `ocp_version` | `"1.0"` | ✅ | 与全仓对象一致；将来 claims 结构变更时，验证方需要据此分派解析逻辑，否则只能猜 |
| `kind` | `"AttributionToken"` | ✅ | 判别器。商户的回报通道会同时收到多种 OCP 对象，没有它就要靠字段形状猜 |
| `jti` | string | ✅ | **防重放的唯一依据**。删掉它，同一凭证可被无限次用于不同订单 |
| `iss` | string | ✅ | 签发节点的 `catalog_id`。**验证方据此定位 JWKS**，删掉它就找不到公钥 |
| `iat` | timestamp | ✅ | 签发时刻。既是 §7 last-touch 裁决的输入，也是 `occurred_at` 下界检查的依据 |
| `exp` | timestamp | ✅ | 有效期上界。删掉它，泄露的凭证永久有效，且归因窗口无法收敛 |
| `agent_id` | string | ✅ | **结算主体之一**。整个协议就是为了确定这个值，删掉它协议无意义 |
| `agent_identity_source` | enum | — | 取值 `ocp` / `external`。留口子给与 Visa TAP / AP2 代理身份的对齐（见 §11）。**默认 `ocp`**；不填即 `ocp`，不构成额外负担 |
| `entry_id` | string | ✅ | 目录内的条目标识。争议复盘时，需要能回到「当时送出去的是哪条」 |
| `object_id` | string | ✅ | Provider 侧的对象标识。**商户的订单只认自己的 ID**，没有它商户无法把凭证与订单行对上 |
| `provider_id` | string | ✅ | 应付方。商户收到凭证的第一步是「这是不是给我的」，删掉它每条凭证都得全量验签才能筛掉 |
| `purpose` | enum | ✅ | 复制自 resolve 请求。**只有 `"checkout"` 可结算**（§7.1）。删掉它，`view` 意图产生的凭证与成交意图无法区分 |
| `complete` | boolean | ✅ | 链是否完整。**非权威**，验证方必须重算（§5.3）。保留它是因为不验签的中间方也需要这个信息，且不一致本身是篡改信号 |
| `chain` | array | ✅ | 逐跳署名与签名。**签名全部挂在这里**，token 本身没有独立签名字段 |

**不在 v1 的字段及理由**（避免后来者重新提出）：

| 被否字段 | 否决理由 |
|---|---|
| `sub` / `aud` | JWT 习惯字段，但本协议的主体已由 `agent_id` + `provider_id` 明确表达，重复表达会产生两个可能冲突的真相源 |
| `amount` / 预估金额 | 签发时不知道成交金额。放一个猜测值只会被误当作结算依据 |
| `user_id` / 任何用户标识 | 见 §9。归因不需要知道是谁买的，只需要知道是谁带来的 |
| `nonce`（独立于 `jti`） | `jti` 已承担唯一性与防重放，两个字段做一件事必然出现「按哪个去重」的争议 |
| `campaign_id` / `channel` | 无消费方。等真实结算场景提出需求再加，加字段比删字段容易 |

### 4.2 token 本身不签名

签名**全部**位于 `chain` 的每个节点内。最后一跳的签名覆盖了 core claims 与全部链前缀，因此对整个 token 的完整性保护是完备的。

单独再加一个 token 级签名会产生「两个签名不一致时听谁的」的歧义。

### 4.3 core claims 的定义

**core claims** = token 去掉 `complete` 与 `chain` 之后的全部字段，即：

```text
ocp_version, kind, jti, iss, iat, exp,
agent_id, agent_identity_source?, entry_id, object_id, provider_id, purpose
```

core claims 在整条链上**不可变**。任何一跳修改 core claims，都会导致其自身及后续所有跳的签名验证失败。

`complete` 不在 core 内，因为它是派生值（§5.3）；`chain` 不在 core 内，因为它是签名的容器。

### 4.4 链长上限

`chain` 长度**必须**在 `1` 到 `8` 之间。

理由：上限不是性能考虑，是**攻击面控制**。无上限意味着验证方要为一条凭证做无界次数的签名验算，这是廉价的放大型拒绝服务。8 跳远超实际拓扑深度。

## 5. AttributionChainNode

### 5.1 字段

| 字段 | 类型 | 必填 | 存在理由 |
|---|---|---|---|
| `catalog_id` | string | ✅ | 本跳节点标识（对应 schain 的 `asi`）。**结算主体之二**，也是 JWKS 发现的输入 |
| `hop` | integer ≥1 | ✅ | 1 起的序号。删掉它，重排链的攻击无法与合法链区分；它也是「篡改定位到第几跳」的表达手段 |
| `role` | enum | ✅ | `origin`（签发首跳）/ `relay`（转发跳）。删掉它，无法表达「谁最先把对象拿出来」 |
| `settles` | boolean | ✅ | 本跳是否参与资金流（对应 schain 的 `hp`）。**不是每个中继都要分钱**。删掉它，结算方只能假定「所有跳都要钱」，与事实不符 |
| `chain_complete` | boolean | ✅ | 本跳声明：截至本跳，链中不存在未记录的上游跳。是 §5.3 重算的输入 |
| `alg` | `"EdDSA"` | ✅ | 签名算法。**必须在签名材料内**，否则存在算法混淆攻击 |
| `kid` | string | ✅ | 密钥标识。节点轮换密钥后，验证方据此在 JWKS 里取对的那把公钥 |
| `signed_at` | timestamp | ✅ | 本跳签名时刻。**last-touch 裁决取最后一跳的该值**（§7.2） |
| `signature` | base64url string | ✅ | 对 §5.2 签名输入的 Ed25519 签名 |

### 5.2 签名输入（规范性）

第 N 跳的签名输入定义为：

```text
signing_input_N = OCP-JCS-v1( {
  "chain": [ unsigned(node_1), unsigned(node_2), ..., unsigned(node_N) ],
  "core":  <token 的 core claims，见 §4.3>
} )
```

其中 `unsigned(node)` = 该节点对象**删去 `signature` 字段**后的其余全部字段。

> 注意 `"chain"` 排在 `"core"` 前面：这不是作者偏好，而是 OCP-JCS v1 §5 键序规则的结果（`chain` < `core`）。实现**不需要**关心这个顺序——规范化函数会处理。此处列出仅为便于人工核对。

签名值为 `Ed25519(privkey_N, signing_input_N)`，以 base64url（无填充）编码。

**这条定义蕴含了三条性质**：

1. 第 N 跳的签名覆盖了第 1..N−1 跳的**全部字段**，因此任何一跳的历史声明都不可被后来者篡改
2. 修改第 K 跳会使第 K..N 跳的签名全部失效，**最小的失效跳号即篡改位置**
3. core claims 被每一跳覆盖，`agent_id` 等关键字段的篡改在第 1 跳就会暴露

### 5.3 `complete` 的重算规则（规范性）

```text
recomputed_complete = chain[0].chain_complete AND ... AND chain[n-1].chain_complete
```

验证方**必须**重算，**禁止**直接采信 token 顶层的 `complete`。

若 `token.complete != recomputed_complete`，验证**失败**，错误码 `complete_mismatch`。

理由：顶层 `complete` 是给不验签的中间方看的便利字段；同时，由于它不在任何签名材料内，一处不一致就是廉价的篡改探针。

### 5.4 链结构校验（规范性）

验签之前**必须**先做结构校验，任一条不满足即失败，错误码 `chain_broken`：

1. `chain` 长度在 `[1, 8]` 内
2. `chain[i].hop == i + 1`（连续、从 1 开始、无重复、无跳号）
3. `chain[0].role == "origin"`，且其余节点 `role == "relay"`
4. `chain` 中 `catalog_id` **不重复**——同一节点在一条链里出现两次是环路，不是合法拓扑

先做结构校验的理由：结构错误的链不值得为它做 8 次签名验算。

## 6. ConversionReport

### 6.1 字段

| 字段 | 类型 | 必填 | 存在理由 |
|---|---|---|---|
| `ocp_version` | `"1.0"` | ✅ | 同 §4.1 |
| `kind` | `"ConversionReport"` | ✅ | 同 §4.1 |
| `report_id` | string | ✅ | **回报本身的**幂等键。网络重试会重复投递，没有它无法区分「重试」与「新回报」 |
| `order_id` | string | ✅ | 商户订单标识。**结算去重的唯一依据**（对应联盟的 `txn_id`）。与 `report_id` 分开是因为一笔订单可能有多次状态回报（成交 → 退款） |
| `provider_id` | string | ✅ | 回报方。**必须**等于 token 的 `provider_id`，否则 A 商户可为 B 商户的凭证造回报 |
| `attribution_token` | AttributionToken | ✅ | 内嵌完整 token，使回报**自包含**：第三方拿到一条回报即可离线复核，无需回查目录节点 |
| `amount_minor` | integer | ✅ | 成交金额，最小货币单位（§2.3）。分账的计算基数 |
| `currency` | ISO 4217 | ✅ | 三字母大写。`amount_minor` 脱离币种无意义 |
| `occurred_at` | timestamp | ✅ | 成交时刻。**不是回报时刻**——回报可延迟，窗口检查（§7.1）必须用成交时刻 |
| `status` | enum | ✅ | `confirmed` / `pending` / `refunded` / `cancelled`。**退款客观存在**，没有它结算无法冲正，每个接入方都会自己发明一套 |

### 6.2 为什么 ConversionReport 在 v1 不签名

商户对回报签名只能证明「这条回报来自该商户且未被篡改」。它**不能**证明商户报全了、报准了——漏报与虚报在签名模型下完全合法。

因此 v1 将回报通道的完整性交给传输层（mTLS / 既有商户鉴权），**内嵌的 token 才是被密码学验证的部分**。

商户签名进 backlog：它的真实价值是在商户否认自己发过某条回报时提供不可抵赖性，属于争议处理增强，不是链路成立的前提。

## 7. 裁决规则

**规则必须成文。** 多个凭证争同一订单时若无成文规则，各结算方会各自解释，对账必然出分歧。

### 7.1 资格过滤（先做）

进入裁决前，每个候选凭证**必须**通过以下全部检查。任一失败即出局，不参与裁决：

| # | 检查 | 失败错误码 |
|---|---|---|
| 1 | 链结构校验通过（§5.4） | `chain_broken` |
| 2 | `complete` 重算一致（§5.3） | `complete_mismatch` |
| 3 | 每一跳签名验证通过（§5.2） | `signature_invalid`（附 `hop`） |
| 4 | 每一跳的 `kid` 在其 `catalog_id` 的 JWKS 中可解析 | `key_not_found`（附 `hop`） |
| 5 | 每一跳 `alg == "EdDSA"` | `alg_not_supported`（附 `hop`） |
| 6 | `token.purpose == "checkout"` | `purpose_not_settleable` |
| 7 | `report.provider_id == token.provider_id` | `provider_mismatch` |
| 8 | `occurred_at >= token.iat` | `token_not_yet_valid` |
| 9 | `occurred_at <= token.exp` | `token_expired` |
| 10 | `token.jti` 未被用于**其他** `order_id` | `replayed_jti` |
| 11 | `report.order_id` 未被结算过 | `duplicate_order` |

> 第 10 条与第 11 条的区别很重要：同一 `jti` 在**同一** `order_id` 上重复出现是正常的（重试、状态更新），在**不同** `order_id` 上出现是重放攻击。

### 7.2 默认规则：last-touch

在通过资格过滤的候选中：

1. 取每个凭证**最后一跳**的 `signed_at`，**最大者胜**
2. 若并列，取 `jti` 的**字典序最小者**胜

第 2 条不是形式主义：没有确定性的平局打破规则，「各方独立算得出同一结果」这个性质就不成立，时钟精度相同的两个凭证会让两个结算方得出不同答案。

### 7.3 结算主体

获胜凭证的结算主体为：

- **代理侧**：`token.agent_id`
- **目录侧**：`chain` 中所有 `settles == true` 的节点的 `catalog_id`

节点之间如何分配比例**不由本协议定义**（§1.1 非目标）。本协议只负责回答「哪些主体有资格分」。

### 7.4 可配置性

last-touch 是**默认值**，不是唯一值。结算方可配置为 first-touch（取 `chain[0]`）或按跳均分。

**但配置必须公开**：任何偏离默认规则的结算方必须在其接入文档中写明所用规则，否则代理方无法预期自己的收入。

## 8. 失败语义

与 OCP-JCS v1 §11 同构：**失败必须是可判定的，而不是「报个错」**。三个独立实现必须对同一条坏凭证给出同一个错误码，否则一致性测试形同虚设。

| 错误码 | 触发条件 | 附加字段 |
|---|---|---|
| `chain_broken` | §5.4 任一条不满足 | — |
| `complete_mismatch` | 顶层 `complete` ≠ 重算值 | — |
| `signature_invalid` | 某跳签名验证失败 | `hop` |
| `key_not_found` | `kid` 在该节点 JWKS 中不存在 | `hop` |
| `alg_not_supported` | `alg` 非 `EdDSA` | `hop` |
| `token_expired` | `occurred_at > exp`，或验证时刻 `> exp` | — |
| `token_not_yet_valid` | `occurred_at < iat` | — |
| `replayed_jti` | 同一 `jti` 用于不同 `order_id` | — |
| `duplicate_order` | 同一 `order_id` 重复结算 | — |
| `provider_mismatch` | 回报 `provider_id` ≠ token `provider_id` | — |
| `purpose_not_settleable` | `purpose != "checkout"` | — |

**验证顺序固定为 §7.1 表格的行序**，且遇首个失败即终止。固定顺序的理由：一条同时违反多项的凭证，若顺序不定，不同实现会报不同的码，测试向量无法断言。

## 9. 隐私

归因凭证**禁止**包含任何终端用户标识：不含 user_id、设备标识、IP、邮箱、订单收货信息。

理由：归因只需回答「谁带来的」，不需要回答「谁买的」。凭证会流经多个目录节点与商户，携带用户数据会把一条结算凭证变成一条跨主体的用户数据通路。

`entry_id` / `object_id` / `order_id` 是**对象与交易**标识，不是用户标识。商户侧的 `order_id` 能反查到用户，但那是商户自己库里的事，凭证本身不承载。

activity 事件侧的归因关联（`correlation_id`）沿用既有的隐私投影模式——公开投影只出 `correlation_id_hash`。该项在 backlog，不在本期。

## 10. 与既有 schema 的挂载点

本协议对既有 Zod schema 的改动**全部为可选字段**，不含破坏性变更。

| 位置 | 新增字段 | 类型 | 性质 |
|---|---|---|---|
| `resolveRequestSchema` | `attribution_context` | `AttributionContext` | 可选 |
| `actionBindingSchema` | `attribution` | `AttributionToken` | 可选 |

**`catalogQueryRequestSchema` 是 `.strict()`，本协议不碰**（§2.1）。

### 10.1 AttributionContext

由代理或中继节点在 `resolve` 请求中提供：

| 字段 | 必填 | 存在理由 |
|---|---|---|
| `agent_id` | ✅ | 节点无法从请求的其他任何部分推断结算主体，必须由请求方声明 |
| `agent_identity_source` | — | 同 §4.1，默认 `ocp` |
| `upstream_token` | — | 中继场景：上游节点签发的 token。**有它才有多跳**；没有它，节点按 `origin` 签发新链 |

### 10.2 兼容性要求（规范性）

**不含 `attribution_context` 的 resolve 请求必须继续通过校验**，行为与本协议引入前完全一致（节点不签发凭证）。

**不含 `attribution` 的 action binding 必须继续通过校验**。凭证是增量能力，不是准入条件。
