# OCP Canonical JSON v1.0

## 1. 文档定位

本文档定义 OCP 协议族在**签名与哈希**场景下使用的 JSON 规范化（canonicalization）规则，记为 **OCP-JCS v1**。

规范化的唯一目的：让**语义相同的 JSON 对象，在任何语言、任何实现下，都产生逐字节相同的输出**。签名验证对字节敏感，这条性质不成立，整条加密链路就不成立。

本文档不定义签名格式、密钥发现或验签流程。那些由 `docs/specs/crypto/v1.md` 定义（W3 产出）。本文档只回答一个问题：**给定一个 JSON 值，它唯一的字节表示是什么。**

适用对象（截至本版本）：

```text
CatalogManifest        签名对象      → crypto/v1.md
SignatureEnvelope      payload_hash  → crypto/v1.md
AttributionToken       claims 序列化 → attribution/v1.md
CatalogRouteHint       manifest_hash → registration/v1.md §16
```

---

## 2. 设计目标

### 2.1 与 RFC 8785 的关系

OCP-JCS v1 是 [RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785) 的**真子集**。

任何符合 OCP-JCS v1 的输入，其 OCP-JCS 输出与 JCS 输出**逐字节相同**。反之不成立——JCS 接受的某些输入被 OCP-JCS v1 拒绝（见 §7）。

这意味着：已有 JCS 实现的语言可以直接复用，只需在前面加一道输入校验。

### 2.2 失败必须关闭

规范化遇到任何不符合本规范的输入，**必须报错终止，禁止猜测、截断或静默修正**。

理由：规范化的下游是签名。一个"尽力而为"的规范化实现会把语义歧义变成签名歧义，而签名歧义等于可伪造。宁可拒签，不可错签。

### 2.3 三语言可独立实现

本仓库有 TypeScript / Python / Go 三套 examples。本规范的每一条规则都必须能用各语言**标准库**实现，不引入第三方依赖。这个约束直接决定了 §7 数字规则的分级。

---

## 3. 术语

| 术语 | 含义 |
|---|---|
| **规范化输入** | 一个已解析的 JSON 值（不是字节流，不是语言原生对象） |
| **规范化输出** | 一个 UTF-8 字节序列 |
| **代码单元序** | 按 UTF-16 code unit 逐个比较的字典序，非码点序、非 UTF-8 字节序 |
| **安全整数** | 绝对值 ≤ `9007199254740991`（即 2⁵³−1）的整数 |

本文档中「必须」「禁止」「应当」按 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 理解。

---

## 4. 处理流程

### 4.1 三个阶段

```text
wire bytes  ──①解析──▶  JSON 值  ──②准入校验──▶  合规值  ──③序列化──▶  canonical bytes
                                      │
                                      └─ 不合规 → 报错终止（§2.2）
```

**②准入校验必须独立于③序列化存在。** 把校验混进序列化过程，会导致部分实现"边写边发现问题"，此时已有字节被写出，错误处理路径难以统一。

### 4.2 顶层约束

- 规范化输入的顶层**必须**是 JSON object。禁止对顶层数组、字符串、数字、布尔、null 做规范化。
- 输出**必须**是 UTF-8，**禁止** BOM，**禁止**结尾换行。
- 输出中**禁止**出现任何非结构性空白：`:` 与 `,` 前后无空格，无缩进，无换行。

### 4.3 签名字段的排除

被签名对象自身携带签名字段时，规范化**之前**必须先移除该字段。具体移除哪个字段由 `crypto/v1.md` 定义，本文档不涉及。

## 5. 规则一：键序

### 5.1 规则

Object 的成员**必须**按成员名的 **UTF-16 代码单元序**升序排列。

排序在**每一层**独立进行。嵌套 object 各自排序，与父层无关。

### 5.2 为什么是 UTF-16 代码单元序，而不是码点序

这是本规范最容易被实现错的一条。

对 BMP 内字符（U+0000–U+FFFF），代码单元序、码点序、UTF-8 字节序三者一致。对 BMP 外字符（U+10000 及以上）三者分歧：

| 成员名 | UTF-16 代码单元 | 码点 | UTF-8 字节 |
|---|---|---|---|
| `"�"` （U+FFFD） | `FFFD` | `0x00FFFD` | `EF BF BD` |
| `"😀"`（U+1F600 😀） | `D83D DE00` | `0x01F600` | `F0 9F 98 80` |

按代码单元序：`D83D` < `FFFD`，**😀 排在前**。
按码点序或 UTF-8 字节序：`0x00FFFD` < `0x01F600`，**U+FFFD 排在前**。

结论相反。而这三种序恰好分别是三种语言的默认行为：

- **TypeScript** `Array.prototype.sort()` 默认按 UTF-16 代码单元 → **正确**
- **Python** `sorted()` 按码点 → **错误**，必须改为 `key=lambda k: k.encode('utf-16-be')`
- **Go** `sort.Strings()` 按 UTF-8 字节 → **错误**，必须转 UTF-16 后比较

### 5.3 为什么不干脆禁止非 ASCII 键名

因为做不到。`packages/ocp-schema/src/index.ts` 中存在自由键名容器，例如 `actionBindingSchema.auth_requirements` 与 `input_schema` 均为 `z.record(z.string(), z.unknown())`，键名不受 schema 约束，可以是任意字符串。

只要签名对象里存在一个自由键名容器，就必须定义完整的排序规则。

### 5.4 重复键

规范化输入中出现重复成员名时**必须**报错终止。

理由：JSON 解析器对重复键的处理是"后者胜"（TS、Go）或实现定义（部分语言），且不同解析器可能取不同的值。攻击者可构造一份 payload，使签名方看到 `{"amount":1,"amount":9999}` 中的 `1` 而消费方看到 `9999`——签名合法，语义不同。这是签名旁路，不是格式问题。

标准库解析器通常会静默去重，因此重复键检测**必须在解析阶段**完成（自定义解析回调或原始字节扫描），不能等到拿到解析结果之后。

## 6. 规则二：字符串与 Unicode 转义

### 6.1 规则

字符串**必须**用 `"` 包裹，内部按下表逐码点处理：

| 输入码点 | 输出 |
|---|---|
| U+0008 | `\b` |
| U+0009 | `\t` |
| U+000A | `\n` |
| U+000C | `\f` |
| U+000D | `\r` |
| U+0022 `"` | `\"` |
| U+005C `\` | `\\` |
| 其余 U+0000–U+001F | `\u00` + **两位小写十六进制** |
| 其他所有码点 | **原样输出为 UTF-8 字节** |

即：**最小转义**。除上表列出的以外一律不转义。

### 6.2 明确不转义的字符

以下字符**禁止**转义，必须原样输出：

- `/`（U+002F）——JSON 允许写成 `\/`，本规范禁止
- `<` `>` `&`（U+003C / U+003E / U+0026）
- 所有非 ASCII 字符，包括中文、emoji、U+007F（DEL）

### 6.3 三处语言默认值陷阱

| 语言 | 默认行为 | 后果 | 必须做的事 |
|---|---|---|---|
| **Go** | `encoding/json` 默认对 `<` `>` `&` 做 HTML 转义（输出 `<` 等） | 与另两种语言字节不同 | `Encoder.SetEscapeHTML(false)`，或不使用 `encoding/json` 序列化 |
| **Python** | `json.dumps` 默认 `ensure_ascii=True`，把所有非 ASCII 转成 `\uXXXX` | 中文字段全部变形 | `ensure_ascii=False` |
| **Python** | `json.dumps` 默认 `separators=(', ', ': ')` 带空格 | 输出含空白 | `separators=(',', ':')` |

这三条是本规范落地时最高频的失败原因。W1-T2 的测试向量**必须**各自覆盖一条。

### 6.4 非法 Unicode

规范化输入中出现**孤立代理项**（lone surrogate，U+D800–U+DFFF 未成对）时**必须**报错终止。

理由：孤立代理项无法编码为合法 UTF-8，各语言的处理方式不同（替换为 U+FFFD、抛异常、或写出 WTF-8），无法保证字节一致。

## 7. 规则三：数字表示

### 7.1 分级

本规范定义两个一致性级别：

| 级别 | 范围 | 本期状态 |
|---|---|---|
| **Level 1 · 整数子集** | 只接受安全整数 | ✅ **必须实现** |
| **Level 2 · 完整双精度** | 按 RFC 8785 §3.2.2.3 的 ECMAScript `Number::toString` 语义处理 IEEE-754 双精度 | ⛔ **v1 不实现**（见 §7.4） |

### 7.2 Level 1 规则

规范化输入中的每个 JSON number **必须**满足：

1. 其数学值是整数（`1.0` 合规且输出 `1`；`0.5` 不合规）
2. 绝对值 ≤ `9007199254740991`（2⁵³−1）

不满足任一条件时**必须**报错终止。

输出格式：

- 可选前导 `-`，随后十进制数字
- **禁止**前导零（`0` 本身除外）
- **禁止** `+` 号、小数点、指数部分
- `-0` **必须**输出为 `0`

各语言的整数判定（均为标准库）：

```text
TypeScript   Number.isInteger(v) && Math.abs(v) <= Number.MAX_SAFE_INTEGER
Python       float(v).is_integer() and abs(v) <= 9007199254740991
Go           v == math.Trunc(v) && math.Abs(v) <= 9007199254740991
```

### 7.3 2⁵³−1 上界为什么是必需的

Go 的 `int64` 能精确表示 2⁶⁰，TypeScript 的 `JSON.parse` 不能。若 Go 侧签名方写出 `1152921504606846976`，TS 侧验签方解析后得到 `1152921504606846976`（恰好可表示）或邻近值（不可表示时静默取近似），重新规范化得到不同字节，验签失败——且失败原因极难定位。

**该上界必须在签名侧和验签侧同时强制**。只在一侧检查等于没检查。

### 7.4 为什么 v1 不做浮点

RFC 8785 要求浮点数按 ECMAScript `Number::toString` 输出，即"最短往返表示 + 特定指数阈值规则"。

- Go `strconv.FormatFloat(f, 'g', -1, 64)` 是最短往返，但指数形式的阈值和格式与 ECMAScript 不同
- Python `repr(float)` 同样是最短往返，指数格式同样不同

两者都需要额外的格式修正层，且边界情形（`1e21`、`5e-7`、次正规数）极难穷尽测试。这与 §2.3「标准库可实现」直接冲突。

**代价是明确的**，不隐瞒：

| 对象 | 数值字段 | Level 1 下可否签名 |
|---|---|---|
| `CatalogManifest` | 全部为 `"type": "integer"`（`max_fanout` / `timeout_ms` / `ttl_seconds` / `catalog_entry_count`） | ✅ **可以** |
| `AttributionToken` | 仅时间戳与计数 | ✅ 可以 |
| `CatalogHealth` | `latency_ms` 为 `"type": "number"` | ❌ 不可以 |
| `pack.ocp.commerce.price.v1` | `amount` / `list_amount` 为 `"type": "number"` | ❌ 不可以 |

即：**Level 1 完整覆盖本期（W1–W7）的签名范围，但不覆盖健康检查响应和商品价格。**

若未来需要对含金额的对象签名，**首选方案不是实现 Level 2，而是把金额改为最小单位整数或字符串**（`{"currency":"CNY","amount_minor":12900}`）。浮点数本就不应承载金额。

### 7.5 非有限值

`NaN`、`Infinity`、`-Infinity` 不是合法 JSON，规范化输入中出现时**必须**报错终止。语言原生对象序列化前需自行检查（Go 的 `encoding/json` 会报错，Python 的 `json.dumps` 默认**会静默写出** `NaN`，需 `allow_nan=False`）。

## 8. 规则四：空值与缺省

### 8.1 null 保留

JSON `null` **必须**原样输出为 `null`。**禁止**删除值为 `null` 的成员。

### 8.2 缺省 ≠ null

「成员不存在」与「成员存在且值为 null」是两个不同的值，规范化输出不同：

```text
{"a":1}            →  {"a":1}
{"a":1,"b":null}   →  {"a":1,"b":null}
```

规范化过程**禁止**增加或删除任何成员。

### 8.3 空容器保留

`[]` 输出 `[]`，`{}` 输出 `{}`。**禁止**删除空数组或空对象成员。

### 8.4 数组顺序是语义

数组元素顺序**必须**原样保留。**禁止**排序、去重。

排序只作用于 object 成员名（§5），不作用于数组。

### 8.5 语言陷阱

| 语言 | 陷阱 | 必须做的事 |
|---|---|---|
| **Go** | `nil` slice 序列化为 `null`，空 slice 序列化为 `[]`；`nil` map 同理 | 规范化输入禁止携带 `nil` slice/map，须先归一化 |
| **Go** | 结构体 tag `omitempty` 会删除空字符串、零值整数、空容器 | 被签名结构体**禁止**使用 `omitempty` |
| **Python** | `None` 与缺失键在 `dict` 中可区分，但部分 ORM/序列化层会合并 | 规范化前不得经过任何"清洗空值"的中间层 |

## 9. 规则的作用层：必须是解析结果，不是校验结果

### 9.1 规则

规范化**必须**作用于 wire bytes 的**直接解析结果**。**禁止**作用于 Zod `parse()` 的输出。

### 9.2 理由

`packages/ocp-schema/src/index.ts` 中存在 **96 处 `.default(...)`**。Zod 的 `.default()` 在 `parse()` 时会**注入**原本不存在的成员。例如 `actionBindingSchema`：

```ts
auth_requirements: z.record(z.string(), z.unknown()).default({}),
requires_user_confirmation: z.boolean().default(false),
```

对不含这两个成员的 wire bytes：

```text
JSON.parse(bytes)                    → {"action_id":"a1", ...}
actionBindingSchema.parse(...)       → {"action_id":"a1", ..., "auth_requirements":{}, "requires_user_confirmation":false}
```

两者规范化输出不同，哈希不同。若签名方在 parse 前规范化、验签方在 parse 后规范化（或相反），**每一次都会验签失败**，且失败与内容无关，排查方向极易跑偏到密钥或算法上。

### 9.3 落地要求

校验与规范化**必须是两条并行分支，不是串行管线**：

```text
                ┌──▶ Zod 校验  ──▶ 业务处理
wire bytes ──解析┤
                └──▶ 规范化    ──▶ 哈希/签名
```

`packages/ocp-crypto` 的公开 API **禁止**接受 Zod schema 参数，以免调用方误以为该包会顺带做校验。

## 10. 哈希表示

canonical 字节的哈希**必须**表示为：

```text
sha256:{64 位小写十六进制}
```

前缀 `sha256:` 为算法标识，为将来更换算法预留。**禁止**省略前缀，**禁止**使用大写十六进制或 base64。

该表示用于 `SignatureEnvelope.payload_hash` 与 `CatalogRouteHint.trust_profile.manifest_hash`。

---

## 11. 一致性测试要求

实现**必须**通过 `packages/ocp-crypto/fixtures/canonical/` 下的全部测试向量。向量为三语言共用，格式为：

```jsonc
{
  "name": "key-order-astral-plane",
  "reason": "UTF-16 代码单元序与码点序结论相反",
  "input": { "�": 1, "😀": 2 },
  "expected_canonical": "{\"😀\":2,\"�\":1}",
  "expected_sha256": "sha256:..."
}
```

拒绝类向量用 `expected_error` 取代后两个字段。

向量集**必须**覆盖以下类别，每类至少一条（详细清单为 W1-T2 交付物）：

1. 键序：ASCII、大小写混合、前缀关系（`a` / `ab`）、非 BMP 字符
2. 嵌套：多层 object 各自独立排序
3. 转义：七个短转义、`U+000B`（无短转义形式，走 `\u000b`）、`/`、`<` `>` `&`、中文、emoji
4. 数字：`0`、`-0`、`1.0`、2⁵³−1 边界、2⁵³、`0.5`（拒绝）
5. 空值：`null` 保留、空容器保留、数组顺序保留
6. 拒绝类：重复键、孤立代理项、`NaN`、顶层非 object

**向量优先覆盖边界与拒绝情形。** happy path 在任何实现里都会过，它不提供信息。

---

## 12. 边界与非目标

本规范**不**定义：

- 签名算法、密钥格式、密钥发现（→ `crypto/v1.md`，W3）
- 签名字段在对象中的位置（→ `crypto/v1.md`，W3）
- 归因凭证的 claims（→ `attribution/v1.md`，W5）
- 加密（本规范只服务于签名与哈希，不涉及机密性）
- JSON 之外的编码（CBOR、protobuf 等）

本规范**不**接受：

- 非整数数值（§7.2）
- 顶层非 object（§4.2）
- 重复键、孤立代理项、非有限值（§5.4、§6.4、§7.5）

---

## 13. 最终原则

1. **语义相同则字节相同**，这是唯一目标，其余规则都是手段。
2. **不合规必须拒绝，禁止修正。** 规范化的下游是签名，静默修正等于把语义歧义升级成签名歧义。
3. **规范化作用于解析结果，不作用于校验结果。** 校验会改变数据。
4. **子集优于完备。** 拒绝浮点数换来三语言可用标准库独立实现，这个交换是划算的。
