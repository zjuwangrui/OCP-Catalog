# OCP Document Signing v1.0

## 1. 文档定位

本文档定义 OCP 协议族的**文档签名**：一个 OCP JSON 文档如何被其签发节点签名，以及第三方如何独立验证这个签名。

本文档回答三个问题：

1. **签什么**——签名对象的范围（§4）
2. **怎么验**——验签流程与固定顺序（§7）
3. **失败了算什么**——稳定错误码与信任降级（§8、§9）

本文档**不**定义 canonical 字节表示，那是 [OCP Canonical JSON v1](./canonicalization.md)（OCP-JCS v1）的职责；本文档所有 `OCP-JCS-v1(...)` 记号均指该规范的输出。本文档也**不**定义归因链的逐跳签名，那是 [attribution/v1.md](../attribution/v1.md) §5.2——两者用同一套密钥与同一套 canonical 规则，但签名材料不同，不可互换。

适用对象（截至本版本）：

| 对象 | 层级 | 状态 |
|---|---|---|
| `CatalogManifest` | T1 | 本版本定稿 |
| `WellKnownCatalogDiscovery` | T1 | 本版本定稿 |
| `ResolvableReference` / `ActionBinding` | T2 | 由归因凭证覆盖，见 attribution/v1.md |
| `ObjectSyncRequest` 等上行数据 | T3 | 未定 |

### 1.1 明确的非目标

- **不做加密**。本文档只做真实性与完整性，不做机密性。OCP 文档是公开文档。
- **不做传输层安全**。TLS 是前提，不是本文档的替代品。签名解决的是「TLS 终止之后、文档被缓存/转发/落库之后」还能不能证明来源。
- **不做证书链与 CA**。信任根是 `catalog_id → discovery → jwks_url` 这条已有路径（§6），不引入 PKI。
- **不做密钥托管与撤销列表**。密钥轮换靠 `kid` 与 JWKS 内容变更，撤销靠把公钥从 JWKS 移除。

## 2. 决策：签名放 body 内嵌，不放 header

**决定：签名信封作为 `signature` 成员内嵌在被签文档中。**

这是 W3-T1 需要落定的决策，理由如下。

### 2.1 为什么是 body

**1. 中间设施会吃掉 header，不会吃掉 body。** CDN、反向代理、API 网关对响应头的处理是各家自定的：改写大小写、合并重复项、按白名单裁剪、在缓存层重建。OCP 节点不控制自己与商户之间的链路，一个「在某些部署下会静默消失」的签名，其失败模式是「验不了」而不是「验不过」，排查成本极高。body 字节要么原样到达，要么请求就失败了。

**2. 文档离开 HTTP 之后签名要还在。** manifest 会被存进注册表、写入缓存、提交进仓库、粘进工单。这些场景里没有 header。一个只活在响应头里的签名，在文档落盘的那一刻就失效了——而落盘之后恰恰是最需要证明来源的时候（`CatalogRouteHint.trust_profile` 存的就是一个离线的 `manifest_hash`，见 registration/v1.md §16）。

**3. OCP-JCS v1 §4.3 已经是按内嵌写的。** 该条规定「被签名对象自身携带签名字段时，规范化之前必须先移除该字段」。canonical 规范预设的就是内嵌形态。

**4. 一次解析，一个对象。** 内嵌意味着验签方拿到的是一个自洽的 JSON 值：文档与它的证明在同一个 parse 结果里，不存在「body 已读完而 header 丢了」的半截状态。

### 2.2 代价，以及为什么接受

内嵌的代价是**边缘设施无法廉价验签**：网关要验签就得解析并规范化整个 body，而不是读一个头。

接受这个代价，因为验签方不是网关。验签方是商户、注册表和目录节点自己——它们本来就要完整解析这份文档才能使用它。为了一个不在设计目标内的角色去牺牲前述四条，不划算。

### 2.3 header 形态不是被否决，是被推后

§5 的信封是**自洽的**：它含 `payload_hash`，因此不依赖自己所在的位置来指认被签对象。这意味着同一个信封可以原样搬进 header 作为一种**传输绑定**（detached 形态），签名字节完全不变。

本版本不定义该绑定。定义它需要回答 header 名、编码（信封是 JSON，header 需要 base64url 或结构化字段）、以及与内嵌形态同时出现时谁优先——三个问题都没有当前用例推动。**内嵌是默认绑定，不是唯一绑定。**

## 3. 术语

| 术语 | 含义 |
|---|---|
| **被签文档**（document） | 携带签名的那个 JSON object，例如一份 `CatalogManifest` |
| **载荷**（payload） | 被签文档**删去 `signature` 成员**后的其余全部内容 |
| **信封**（envelope） | `signature` 成员的值，即 `SignatureEnvelope` |
| **签名材料** | 信封删去 `signature` 字段后的 OCP-JCS 输出，即实际被 Ed25519 签的那串字节 |

「必须」「禁止」「应当」按 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 理解。

## 4. 签名对象的范围（规范性）

### 4.1 两层绑定

签名不直接盖在文档上，而是盖在信封上，信封再通过哈希指向文档：

```text
payload  ──OCP-JCS──▶ canonical bytes ──SHA-256──▶ payload_hash
                                                        │
                                                        ▼
                             envelope{alg,kid,issuer,signed_at,expires_at?,payload_hash}
                                                        │
                                                    OCP-JCS
                                                        │
                                                        ▼
                                                  Ed25519 签名
```

规范性定义：

```text
payload        = document 删去 "signature" 成员
payload_hash   = "sha256:" + hex(SHA-256(OCP-JCS-v1(payload)))
签名材料        = OCP-JCS-v1(envelope 删去 "signature" 字段)
signature      = base64url_unpadded(Ed25519(签名材料))
```

哈希表示遵循 OCP-JCS v1 §10：小写十六进制，`sha256:` 前缀不得省略。

### 4.2 为什么不直接签整份文档

直接签 `{document, meta}` 是更短的写法，但它丢掉两件事。

**第一，失败无法定位。** 两层绑定下，哈希对不上说明**载荷**被改了，签名验不过说明**信封**被改了或者用错了公钥。这是两个完全不同的运维结论：前者是文档在传输/存储中被动过，后者是密钥配置或冒名。单层签名对这两种情况给出同一个「验不过」，而这恰恰是 §8 要求可判定的那类区分。

**第二，无法对着一个手里已有的哈希验证。** 注册表在 `CatalogRouteHint.trust_profile.manifest_hash` 里钉的是一个哈希，不是整份 manifest。两层绑定让「我持有的哈希 == 信封声称的哈希 == 重算出的哈希」成为一条可直接比对的链；把哈希埋进签名材料内部就比不了了。

### 4.3 为什么 alg / kid / issuer 必须在签名材料内

它们在签名材料内，意味着改动其中任何一个都会使签名失效。

- **`alg` 在内**——关掉算法混淆。验签方从签名材料里读算法，而不是从一个攻击者可改写的旁路字段读。这与 attribution/v1.md §5.1 的处理一致，理由也一致。
- **`kid` 在内**——关掉密钥替换。攻击者不能把一个合法签名重新指向自己 JWKS 里的另一把密钥。
- **`issuer` 在内**——关掉冒名。一个节点签发的文档不能被改挂到另一个节点名下。
- **`signed_at` 在内**——签名时刻本身是证据。不签它，回放一份旧 manifest 时可以把时间改成现在。

### 4.4 `issuer` 是 `catalog_id`，不是 URL

`issuer` **必须**等于被签文档的 `catalog_id`。文档没有 `catalog_id` 成员时，`issuer` 必须等于验签方在带外持有的、该文档所属节点的 `catalog_id`。

方案草图里 `issuer` 写的是一个 URL。改掉的理由：OCP 里所有跨主体引用都以 `catalog_id` 为键——归因链的 `chain[].catalog_id`、路由提示的 `catalog_id`、结算主体。再引入一个 URL 身份空间就要处理别名问题（`http` 与 `https`、尾斜杠、`www` 前缀、同一节点的多个域名），而这些别名每一种写法都会产生一个不同的签名。

URL 并没有因此丢失：从 `catalog_id` 找公钥的路径是 §6 的 discovery，URL 在那条路径上，不需要进签名材料。

### 4.5 签名对象必须是解析结果，不是校验结果

**禁止**对 Zod `parse()` 的输出计算 `payload_hash`。

这是 OCP-JCS v1 §9.1 的直接后果，但在 manifest 上后果格外严重：`catalogManifestSchema` 的 `federation` 分支带大量 `.default(...)`，一份线上没有 `federation` 的 manifest 经 `parse()` 后会凭空长出几十个成员。签名方若签 parse 结果、验签方若验 wire 解析结果（或反过来），**每一次都验不过**，且失败与内容无关，排查方向会跑偏到密钥上。

正确做法是 OCP-JCS v1 §9.3 的并行两分支：wire bytes 解析一次，一支去 Zod 校验，一支去规范化签名。

## 5. SignatureEnvelope

Schema：[`ocp.catalog.crypto.v1/signature-envelope.schema.json`](../../../ocp.catalog.crypto.v1/signature-envelope.schema.json)。

### 5.1 字段

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `alg` | ✅ | `"EdDSA"` | v1 只接受 Ed25519。见 §5.2 |
| `kid` | ✅ | string | JWKS 中的密钥标识。应当为该公钥的 RFC 7638 thumbprint |
| `issuer` | ✅ | string | 签发节点的 `catalog_id`，见 §4.4 |
| `signed_at` | ✅ | RFC 3339 | 签名时刻，UTC |
| `expires_at` | — | RFC 3339 | 签名有效期终点。缺省表示不过期，见 §5.3 |
| `payload_hash` | ✅ | `sha256:<64 hex>` | 载荷的 canonical 哈希，见 §4.1 |
| `signature` | ✅ | base64url（无填充） | 对签名材料的 Ed25519 签名 |

**禁止**出现表外字段。信封是签名材料本身，一个验签方不认识的字段要么被忽略（那它就是可以被攻击者塞进去的无签名空间的反面——它进了签名材料却不被检查），要么导致互操作失败。封闭字段集让两种可能都不存在。

### 5.2 为什么只有一个算法

与 attribution/v1.md §5.1 同理：单算法实现无法被降级协商。方案草图写的是「MUST: Ed25519；SHOULD: ES256」，本版本**不收 ES256**——多一个算法就多一条协商路径，而 v1 没有任何用例需要它。`alg` 字段保留为将来扩展的位置，但取值集合在 v1 是单元素集。

`trust_strategy.signature_algorithms` 因此在 v1 只可能是 `[]` 或 `["EdDSA"]`。

### 5.3 `expires_at` 为什么可选

manifest 的正常生命周期是「一直有效直到节点改它」，给签名强加有效期会制造一类纯运维故障：节点内容没变、密钥没变，签名到期了，全网把它降级。

需要有效期的是另一类场景——节点想主动限制一份文档被缓存转发的时长。这是节点的策略，不是协议的要求，所以是可选字段。

写了就必须检查（§7 第 7 步）。

## 6. 密钥发现

不新增发现机制，复用 discovery：

```text
catalog_id ──▶ GET /.well-known/ocp-catalog ──▶ jwks_url ──▶ GET jwks_url ──▶ 按 kid 取公钥
```

`jwks_url` 已在 `wellKnownCatalogDiscoverySchema` 中（为归因验签引入），本文档直接复用。密钥要求与归因一致：`kty: "OKP"`、`crv: "Ed25519"`、`x` 为无填充 base64url 的 32 字节原始公钥；若带 `alg` 必须是 `EdDSA`，若带 `use` 必须是 `sig`。

**先有鸡还是先有蛋：** discovery 文档本身也可签（§1 表格），而它正是找公钥的入口。这不构成循环——第一次取公钥时验签方对该节点还没有信任，签名不改变这一点；签名的价值从第二次开始：一份被缓存或被转发的 discovery 文档能被证明没有被改过。首次信任由 TLS 与域名建立，这是 §1.1 明确的边界。

密钥轮换：节点在 JWKS 中同时列出新旧公钥，用新密钥重签文档，旧密钥在所有引用它的文档都过期后移除。`kid` 取 thumbprint 保证两把不同的密钥不会共用一个标识。

## 7. 验签流程（规范性）

对一份被签文档，**必须**按下表顺序执行，**遇首个失败即终止**并返回对应错误码。

| # | 检查 | 失败码 |
|---|---|---|
| 1 | 文档含 `signature` 成员 | `unsigned` |
| 2 | 信封是 object，§5.1 必填字段齐全、类型与格式正确、无表外字段 | `envelope_malformed` |
| 3 | `alg` 为 `EdDSA` | `alg_not_supported` |
| 4 | `issuer` 等于文档 `catalog_id` | `issuer_mismatch` |
| 5 | 重算载荷哈希，等于 `payload_hash` | `payload_mismatch` |
| 6 | 在该节点 JWKS 中按 `kid` 取到一把可用的 Ed25519 验签公钥 | `key_not_found` |
| 7 | 签名材料的 Ed25519 验证通过 | `signature_invalid` |
| 8 | 若有 `expires_at`，验证时刻 ≤ `expires_at` | `signature_expired` |

### 7.1 顺序的理由

**固定顺序本身是规范要求**，理由与 attribution/v1.md §8 相同：一份同时违反多条的文档，若顺序不定，三个实现会报三个不同的码，一致性向量无法断言。

具体的排法：

- **结构与算法在最前**（1–3）。都是本地检查，不需要网络，也不需要规范化整份文档。
- **`issuer` 在哈希之前**（4）。这是一个字符串比较，能在花费一次全文档规范化之前挡掉挂错名的文档。
- **哈希在取密钥之前**（5 在 6 之前）。一份载荷已经对不上哈希的文档，不值得为它去拉一次 JWKS。这不是性能优化，是拒绝让任意文档驱动本节点发起网络请求。
- **过期在最后**（8）。一个签名正确但过期的文档，与一个伪造的文档是两件事。若把过期检查提前，一份伪造且恰好过期的文档会被报成 `signature_expired`，读日志的人会以为对面只是忘了重签。

### 7.2 验证成功的结论

验签通过**只**证明三件事：

1. 这份载荷的字节自签名以来没有变过；
2. 签名由 `issuer` 声称的节点持有的私钥产生；
3. 签名时刻是 `signed_at`。

它**不**证明载荷内容为真。一个节点完全可以如实签署一份内容虚假的 manifest——签名把「谁说的」钉死，不评价「说得对不对」。`trust_tier` 的语义要按这一条理解（§9）。

### 7.3 JWKS 取不到不是错误码

与 attribution/v1.md §8 的同名条款一致，逐字适用：若该节点的 JWKS 拉不到、已过期或格式损坏，验签方**不得**报 `key_not_found`。密钥服务器宕机的节点没有伪造任何东西。这类情况作为传输层失败向上抛出，由调用方决定重试还是挂起，**不产生验签结论，也不触发 §9 的降级**。

`key_not_found` 的语义严格限定为：JWKS 取到了，里面没有这个 `kid`，或者有但它不是一把可用的 Ed25519 验签公钥。

## 8. 失败语义

| 错误码 | 触发条件 | 是否指向伪造 |
|---|---|---|
| `unsigned` | 文档没有 `signature` 成员 | 否——没有证据，不是反证 |
| `envelope_malformed` | 信封结构不满足 §5.1 | 不确定 |
| `alg_not_supported` | `alg` 非 `EdDSA` | 不确定 |
| `issuer_mismatch` | `issuer` ≠ 文档 `catalog_id` | 是 |
| `payload_mismatch` | 重算哈希 ≠ `payload_hash` | 是——载荷被改 |
| `key_not_found` | `kid` 在该节点 JWKS 中不存在，或存在但不可用于验签 | 不确定 |
| `signature_invalid` | 签名材料验证失败 | 是——信封被改，或非该节点签发 |
| `signature_expired` | 验证时刻 > `expires_at` | 否 |

三个独立实现**必须**对同一份坏文档给出同一个码。这与 OCP-JCS v1 §11 和 attribution/v1.md §8 是同一条要求，理由也相同：「验签失败」在测试里不可判定。

`unsigned` 单列而不是复用 `envelope_malformed`，因为二者的运维动作相反：前者要去问对面「你们打算什么时候开签」，后者要去查「你们的签名实现是不是写错了」。

## 9. 信任降级（规范性）

验签结论决定 `CatalogRouteHint.trust_profile` 与 `trust_strategy.trust_tier` 能取的上限：

| 验签结论 | `trust_tier` 上限 | 缓存 |
|---|---|---|
| 通过 | `verified`（更高的 `trusted` 需要域名验证等带外证据） | 保留 |
| `unsigned` | `unverified` | 保留 |
| `signature_expired` | `unverified` | 保留 |
| 其余任何错误码 | `unknown` | **必须**作废 |

「必须作废」即 `trust_strategy.downgrade_invalidates_cache` 的触发条件。该字段默认 `true`，本文档把它从一个声明变成一条可执行规则：一个节点从「验签通过」掉到 `unknown`，说明此前缓存的内容来源不再可信，继续用它等于把一次已发现的篡改延长一个 TTL。

`unsigned` 与 `signature_expired` 不作废缓存：都没有任何证据表明内容被动过。

**上限不是结论。** 验签通过只是解除了 `verified` 的封顶，具体给什么 tier 由消费方策略决定（§7.2）。

### 9.1 `manifest_signed` 的真实语义

`trust_strategy.manifest_signed` 在此前是一个没人校验的自述字段。本文档定义它的判定：

- 节点**应当**在自己的 manifest 里把它置为 `true` 当且仅当同一份 manifest 携带一个有效信封；
- 验签方**禁止**采信这个字段。`manifest_signed: true` 但文档没有 `signature` 成员，按 `unsigned` 处理并按上表封顶——一个节点声称自己签了名却拿不出签名，不应当比一个老实承认没签名的节点得到更高的信任。

注意 `trust_strategy` 在载荷内部，因此它本身被签名覆盖：声明与证明绑在一起，改声明会导致 `payload_mismatch`。

## 10. 与既有 schema 的挂载点

本协议对既有 schema 的改动**全部为可选字段**，不含破坏性变更。

| 位置 | 新增字段 | 类型 | 性质 |
|---|---|---|---|
| `catalogManifestSchema` | `signature` | `SignatureEnvelope` | 可选 |
| `wellKnownCatalogDiscoverySchema` | `signature` | `SignatureEnvelope` | 可选 |
| `catalog-manifest.schema.json` | `signature` | `$ref` 信封 | 可选 |

两个 Zod schema 均非 `.strict()`，因此 Zod 侧零破坏。`catalog-manifest.schema.json` 顶层是 `additionalProperties: false`，**必须**同步加入 `signature`，否则一份带签名的 manifest 会被 JSON Schema 校验拒绝。

### 10.1 兼容性要求（规范性）

**不含 `signature` 的文档必须继续通过校验**，行为与本协议引入前完全一致。签名是增量能力，不是准入条件。

**验签方不得因为文档无签名而拒绝使用它**，只能按 §9 封顶信任等级。

---

## 11. 一致性测试要求

实现**必须**通过 `packages/ocp-crypto/fixtures/signature/` 下的全部向量，格式与归因向量同构：一份确定性密钥、一份被签文档、其 `expected_payload_hash` 与 `expected_signing_input`、`expected_envelope`，以及一组负例，每条给出**确切的错误码**。

负例**必须**覆盖 §8 的每一个码，且**必须**包含一条「载荷任意一字节被改」——这是 W3-T3 完成判据的机读形态。

`expected_signing_input` 的作用与归因向量里的同名字段一致：签名不一致但签名材料一致，问题在密钥处理；签名材料就不一致，问题在规范化。少了它，「验不过」是两种完全不同缺陷的唯一症状。
